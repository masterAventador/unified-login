  • 本地验签 JWT，不需要回调认证中心

1产品前端把浏览器跳到 auth.域名/oauth2/authorize，带 client_id、redirect_uri、PKCE challenge
2认证中心没有会话 → 显示登录页；已有会话 → 直接回跳，这就是免登
3回调地址收到一次性 code，前端用 code + PKCE verifier 换 access / refresh / id token
4前端带 access token 调本产品的 Python 后端，后端用缓存的公钥本地验签
为什么第 2 步就是 SSO 的全部秘密：会话 Cookie 种在 auth.主域名 自己身上，不是种在产品域上。在 A 产品登录时这个 Cookie 就有了；再去 B 产品，B 把浏览器跳到认证中心，认证中心一看 Cookie 还在，连页面都不渲染就直接回跳 —— 用户感知是「B 产品不用登录」。

2 · 数据模型与 token 策略

认证中心只存「你是谁」，不存任何产品的业务权限

自己写的唯一一张核心表 · app_user

三种 token 的分工与寿命
15 分钟

Access Token（JWT）

调各产品业务接口时带的那个。产品后端本地验签，不回调认证中心。故意做短 —— 它一旦泄漏无法单独撤销，只能等它过期

30 天

Refresh Token

一次性 + 轮转：每次刷新都作废旧的、发一个新的。同一个 refresh token 被用第二次 → 判定为泄漏，该用户所有 token 立即全部作废

5 分钟

ID Token

只在登录完成那一刻用一次，告诉前端「登录的人是谁」。绝不能拿它去调接口

14 天

认证中心会话 Cookie

只种在 auth 子域，各产品拿不到也不需要。它活着 = 免登生效。滑动续期

access token 15 分钟带来的一个真实后果：在管理后台禁用一个用户，他不会立刻掉线，最长还能用 15 分钟。要做到「点了禁用立刻踢出」，唯一办法是产品后端每次请求都回调认证中心查状态 —— 那就丧失了本地验签的全部好处，认证中心一挂全线瘫痪。当前产品量级下接受这 15 分钟延迟。

3 · 浏览器端的三种登录时序

同一套授权码 + PKCE 流程，跑出三种完全不同的用户感受

场景一 · 第一次登录 A 产品

唯一需要用户动手的一次 用户感受：跳到登录页，填邮箱密码，跳回来
前端
生成随机 code_verifier 存起来，算出它的哈希 code_challenge 一起发出去 —— 这一步保证中途被截走的 code 换不到 token
前端
整页跳转到 auth.域名/oauth2/authorize?client_id=…&code_challenge=…
认证中心
没有会话 Cookie → 渲染登录页
认证中心
用户提交邮箱密码 → Argon2id 校验 → 检查账号未被禁用 → 种下 14 天会话 Cookie（只在 auth 子域）
认证中心
302 回跳 a产品.域名/callback?code=一次性码
前端
校验 state 后用 code + code_verifier 换 token，三个 token 到手，全部只放内存

场景二 · 接着去 B 产品

SSO 的兑现时刻 用户感受：点开就是登录状态，什么都没发生
B 前端
同样跳 /oauth2/authorize，带的是 B 自己的 client_id
认证中心
会话 Cookie 还在且有效 → 登录页根本不渲染，直接放行
认证中心
立刻 302 回跳 b产品.域名/callback?code=…
B 前端
换到 token，进入已登录界面。全程约 200ms，用户只可能看到一次地址栏闪烁

场景三 · 用户按了 F5 刷新页面

token 存内存的代价与解法 用户感受：和普通刷新没区别
前端
内存里的 token 随页面一起没了
前端
在隐藏 iframe 里静默请求 /oauth2/authorize?prompt=none
认证中心
会话有效 → 直接回跳带 code；会话已过期 → 返回错误而不是显示登录页（这正是 prompt=none 的作用）
前端
拿回 token，页面继续。若收到错误，才把用户送去登录页
为什么坚持 token 只放内存、不落 localStorage：refresh token 有 30 天有效期，一旦被页面上任何一个第三方脚本或 XSS 偷走，等于账号被接管 30 天，而你无从察觉。放内存则页面一关就没了，代价仅仅是刷新页面时多一次 200ms 的静默握手 —— 而这次握手能成功，恰恰又是因为 SSO 会话本来就在。SSO 让「不存 token」这个安全选择变得没有代价。
静默续签的前置约束：它依赖 iframe 里的请求能带上认证中心的会话 Cookie，这要求产品域与 auth 域属于同一主域名（浏览器视为 same-site）。若未来某个产品部署到完全不同的主域名下，静默续签会失效，该产品需改用整页跳转式续签。本地开发因为都在 localhost 不同端口，同样是 same-site，无法复现这个问题，需在预发环境验证。

4 · 桌面端（Tauri）与移动端

桌面端不自己画登录框 —— 这个反直觉的选择，恰恰是它能享受 SSO 的原因

Tauri 桌面端登录时序

用户感受：点登录 → 浏览器弹出 → （可能已登录，直接完成）→ 回到 App 已是登录态

Rust 侧
在 127.0.0.1 上起一个临时 HTTP 服务，端口随机，只为接这一次回调
Rust 侧
用系统默认浏览器打开 auth.域名/oauth2/authorize?redirect_uri=http://127.0.0.1:随机端口/callback
系统浏览器
如果用户之前在浏览器里登录过任何一个 Web 产品 —— 会话 Cookie 就在这里，认证中心直接放行，登录页都不显示
认证中心
否则渲染登录页，用户填一次邮箱密码
系统浏览器
回跳到 127.0.0.1:端口/callback?code=…，页面显示「登录成功，可以关闭此页」
Rust 侧
校验 state 与预期一致 → 用 code + verifier 换 token → 立即关掉临时服务
Rust 侧
refresh token 写入操作系统凭据库，access token 只留内存
下次启动
从凭据库取回 refresh token 直接换 access token，30 天内不用再登录

refresh token 存哪

各系统的官方凭据库，不是明文文件、不是 localStorage：

macOS 钥匙串Windows 凭据管理器Linux Secret Service

这是桌面端相对 Web 端的优势 —— 浏览器没有等价的安全存储，所以 Web 端才必须靠静默握手。

移动端（未来）

协议完全一样，只有回调方式不同：iOS 用 ASWebAuthenticationSession、Android 用 Custom Tabs，回调走 App Links 或自定义 scheme，凭据存 Keychain / Keystore。

一期不写代码，认证中心侧也不需要为它做任何改动 —— 到时只是配置里多一个 client。

✓ 用系统浏览器登录

  • 和 Web 产品共享会话，真正的全端 SSO
  • 用户能看到 auth.你的域名 和锁标，钓不了鱼
  • 浏览器已存的密码可自动填充
  • App 代码永远碰不到用户密码

✗ 在 App 里内嵌 WebView 画登录框

  • WebView 的 Cookie 是独立的，SSO 直接失效，每个 App 都要单独登录
  • 用户无法确认自己在给谁输密码
  • OAuth 官方规范明确不推荐
  • 第三方登录提供方会直接拒绝

5 · 错误处理与测试策略

登录系统的失败路径比成功路径重要 —— 成功只有一条，失败有十几条

测试分层

单元测试

集成测试

@SpringBootTest + Testcontainers

协议一致性测试

MockMvc

JWKS 端点返回的公钥能验开签发的 token；discovery 文档字段齐全；refresh token 重放必须被拒；回调白名单校验

端到端测试

Playwright

真实浏览器跑：注册 → 登录 demo-web-a → 打开 demo-web-b 验证免登 → 改密 → 验证 refresh 被拒 → 后台禁用 → 验证登不进。纳入仓库可重复执行

必须显式处理的失败路径
情况行为
邮箱已注册提示已存在，不透露该邮箱是否活跃
密码错误与「账号不存在」返回相同提示；不存在时也跑一次等价哈希运算对齐耗时
连续登录失败同邮箱失败 5 次锁 15 分钟；同 IP 每分钟上限 20 次
账号已被禁用登录直接拒绝；已持有的 refresh token 也换不到新 token
refresh token 被重放判定泄漏，该用户全部 token 立即作废
回调地址不在白名单直接报错，绝不回跳 —— 防开放重定向的命门
改密后的旧 token早于 password_changed_at 签发的 refresh token 全部失效
静默续签时会话过期prompt=none 返回错误而非登录页，前端据此跳转
桌面端回调 state 不符丢弃该 code，不换 token，提示重新登录
认证中心不可用已登录用户不受影响（本地验签），仅新登录和续期受阻

demo 接入方（不碰任何现有项目）

SSO 的核心价值是「第二个产品免登」—— 只有一个接入方时，这件事在物理上无法被验证。demo 接入方存在的唯一目的，是让上面那条端到端用例真的能跑起来，并长期留在回归集里。

demo-web-a / demo-web-b两个极简 Vite SPA，各自一个 client_id。存在的意义就是证明免登真的发生
demo-api一个 FastAPI 服务，一个受保护接口，验证 Python 验签依赖真的能用
demo-desktop最小 Tauri 壳，验证 loopback 回调与凭据库存储

6 · 实现阶段划分

每个阶段结束时都必须有一个能用真实用户操作验证的成果

阶段内容阶段结束时可验证的事实
一 · 地基认证中心骨架、app_user 表与迁移、注册、登录页、授权码 + PKCE 流程、demo-web-a能在浏览器完成注册并登录 demo-web-a
二 · SSO 兑现Web TS 套件、静默续签、demo-web-b登录 A 后打开 B 不出现登录页，刷新页面保持登录
三 · 资源服务器Python FastAPI 验签依赖、demo-api带 token 访问受保护接口返回 200，不带返回 401
四 · 账号自服务与管理修改密码、管理 API、管理后台 SPA改密后旧 refresh token 被拒；后台禁用后无法登录
五 · 桌面端Tauri 套件（Rust 回环回调 + 凭据库）、demo-desktop桌面端完成登录，重启后仍是登录态
阶段二是整个项目的价值验证点。若阶段二无法通过，后续阶段的意义都需重新评估。
