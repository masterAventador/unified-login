# 部署注意事项

本文件记录**部署形态会改变代码行为**的约束。这里的每一条都不是建议，改动前必须先读。

## 反向代理与登录限流的客户端地址

登录失败限流按客户端 IP 计数，取值用的是 `HttpServletRequest.getRemoteAddr()`
（见 `LoginRateLimitFilter`）。当前部署形态下它拿到的是真实的 socket 对端地址。

**若在认证中心前面加反向代理（nginx、云负载均衡等），必须同时处理这一点，否则限流会静默失效或误伤：**

| 配置 | `getRemoteAddr()` 返回什么 | 后果 |
| --- | --- | --- |
| 直连，无代理（当前形态） | 真实客户端地址 | 正确 |
| 有代理，未开启转发头支持 | **代理自己的地址** | 所有用户共用一个计数桶，正常流量互相顶掉配额 |
| 有代理，开启 `server.forward-headers-strategy` | `X-Forwarded-For` 的值 | 该值**客户端可伪造**，攻击者每次换一个即可绕过限流 |

第三种最危险，因为它看起来是"正确配置"，但会让 IP 限流完全失去意义。

**要求**：加代理时必须由代理层**覆写**（而非追加）`X-Forwarded-For`，剥掉客户端自带的值，
再开启 `server.forward-headers-strategy: framework`。同时确认代理到认证中心之间的网络不可被
外部直接访问，否则攻击者可绕过代理直连并伪造头。

## 限流计数的单实例约束

邮箱锁定与 IP 限流的计数保存在**应用内存**中（Caffeine）。多实例部署时每个实例各记各的，
攻击者轮换实例即可把有效尝试次数放大到 N 倍。

**要求**：本阶段只能单实例部署。要横向扩展必须先把计数迁移到共享存储（Redis 等）。
这是规格书已登记的取舍，不是疏漏。

## 签名密钥文件

JWT 签名私钥落在 `unified-login.jwt-key-store` 指定的路径，默认 `./data/jwt-signing-key.json`，
文件权限 0600。

**要求**：该文件必须持久化并纳入备份。丢失会导致所有已签发的 access token 与 id token
无法验签，全部用户被迫重新登录。多实例部署时所有实例必须共享同一份密钥。

## issuer 地址

`ISSUER_URL` 会被写进 discovery 文档和每一个 JWT 的 `iss` 声明，各产品后端按它校验令牌来源。

**要求**：必须配置为该环境**对外可访问**的真实地址。配错不会启动失败，但签发出去的令牌
会带着错误的 `iss`，产品侧验签全部失败。改动 issuer 等同于让存量令牌全部失效。
