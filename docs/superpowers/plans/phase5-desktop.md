# 阶段五实现计划：Tauri 桌面端

> **执行前必读**：`docs/HANDOVER.md`、`docs/superpowers/specs/2026-07-29-unified-login-design.md`（重点 §7.4、§8.3）。

**目标：** 桌面端完成登录，重启应用后仍是登录态。

**技术栈：** Tauri 2、Rust、TypeScript 前端。

## Global Constraints

- **HANDOVER.md 的工作纪律全部适用。**
- **绝对禁止在应用内嵌 WebView 中渲染登录页**（规格书 §7.4 明确禁止）。两个理由：WebView 有独立 Cookie 存储，用它登录等于开了个隔离浏览器，**全端 SSO 当场失效**；用户在内嵌 WebView 里看不到地址栏，**无法确认自己在向谁输密码**，这是钓鱼的标准形态。
- 必须调**系统默认浏览器**。好处是顺带白拿 SSO：用户之前在浏览器里登过任一网页产品，桌面端点登录会直接跳回来。
- refresh token 必须存**操作系统凭据库**（macOS 钥匙串 / Windows 凭据管理器 / Linux Secret Service），**不得**明文落配置文件。access token 只存内存。
- 本阶段的可行性**依赖阶段一已打通的"公有客户端能拿到 refresh token"**——框架默认不发，阶段一覆盖了两层拦截才通。若这条被回退，本阶段"重启后仍是登录态"直接落空。
- 提交信息用中文，不加 AI 署名。

### ⚠ 阶段一登记的前瞻约束（本阶段会踩到）

**令牌端点的 CORS 允许来源是从已注册回调地址推导的。** 桌面端的回调是 `http://127.0.0.1:<随机端口>/callback`，端口每次都不同；若把它注册进客户端回调白名单，推导 CORS 来源时会产生一堆无意义条目。

更要紧的是规格书 §6.5 已登记的一条：**推导来源时必须只取 http/https 回调**——阶段五若引入自定义 scheme（如 `myapp://callback`），推导出的"源"没有 host，灌进 CORS 允许列表会导致配置非法甚至启动失败。**本阶段动客户端注册前必须先处理这条。**

## Task 1：回环回调服务

**Files:** `desktop/demo-desktop/src-tauri/src/auth/loopback.rs` + Rust 单元测试

**要求（规格书 §7.4 第 1、4、5 步）：**
- 在 `127.0.0.1` 启动临时 HTTP 服务，**端口由系统随机分配**（绑 `127.0.0.1:0` 再读实际端口）
- 只处理本次登录的一个回调请求
- 回调页面显示"登录成功，可关闭此页"
- 拿到 code 后**立即关闭临时服务**

> ⚠ 回环地址是**本机任何程序都能往里发请求的**。必须校验 `state`（Task 3），不校验等于谁都能塞一个授权码进来。

- [ ] TDD：先写"服务能起来并在随机端口接收一次回调后关闭"的测试

## Task 2：PKCE 与令牌交换

**Files:** `auth/pkce.rs`、`auth/exchange.rs` + 测试

**要求：**
- verifier 用密码学安全随机源取 32 字节后 base64url；challenge 用 S256
- 换令牌与刷新走 `POST /oauth2/token`，**不附加 `Authorization` 头**（HANDOVER 坑 ⑫）
- 刷新失败（refresh token 过期或被撤销）要能区分于网络错误，前者引导重新登录，后者可重试

- [ ] TDD

## Task 3：`state` 校验（安全关键）

**Files:** 在 `loopback.rs` / 登录流程中

**要求：**
- 登录发起时生成 `state`，回调时校验一致
- 不一致 → **丢弃该 code，不换取令牌**，提示重新登录（规格书 §10）

- [ ] **必须做变异测试**：去掉 `state` 校验后，伪造回调的用例必须变红。这是本阶段最重要的一条安全断言

---

## Task 4：系统凭据库

**Files:** `auth/credentials.rs` + 测试

**要求：**
- refresh token 写入系统凭据库；access token **只存内存**
- 读取失败（用户拒绝钥匙串授权、条目被删）要优雅降级到"需要重新登录"，**不要 panic**
- 登出时删除凭据库条目

> 跨平台差异较大，若某平台暂不支持，**明确报告 BLOCKED 并说明**，不要用明文文件兜底——那会让 refresh token 以明文躺在磁盘上 30 天。

- [ ] TDD

## Task 5：调起系统浏览器与完整登录流程

**Files:** `main.rs` 与前端界面

**流程（规格书 §7.4）：**
1. Rust 起回环服务拿到端口
2. 用**系统默认浏览器**打开 `<issuer>/oauth2/authorize?redirect_uri=http://127.0.0.1:<port>/callback&...`
3. 浏览器中已有认证中心会话 → 直接回跳无需输密码；否则渲染登录页
4. 回跳到本地回调，页面显示"登录成功，可关闭此页"
5. 校验 `state` → 换令牌 → 关闭临时服务
6. refresh token 进凭据库，access token 只在内存
7. **下次启动从凭据库取回 refresh token 直接换 access token，30 天内无需重新登录**

- [ ] 先把客户端注册加进 `application.yml`（注意本文档开头的 CORS 前瞻约束）

## Task 6：真实验收（本阶段必须在真实应用里做）

**规格书要求：桌面端交付必须在真实应用里按用户操作方式验收，"网页端过了"不能替代。**

必须验证的场景：
1. 全新安装 → 点登录 → 系统浏览器打开 → 输密码 → 回到应用显示已登录
2. **浏览器里已登录过任一网页产品 → 桌面端点登录直接回跳，一个字都不用输**（这是 SSO 的兑现）
3. **关闭应用再打开 → 仍是登录态**（凭据库生效）
4. 伪造回调（本机发一个 state 不符的请求到回环地址）→ 被拒绝
5. 登出 → 凭据库条目被删 → 重启后需要重新登录

> ⚠ 验收必须在**用户实际拿到的那个构建产物**上做，不是开发模式。规格书的「单一构建路径规范」要求测试构建与生产构建的产品代码逐字相同——如果发现桌面端的依赖解析在两种构建下不同，**停下来报告**，那是必须先解决的结构问题。

1. 全部 Rust 测试与真实应用验收场景通过

4. `state` 校验有变异验证过的测试守护
5. refresh token 确认在系统凭据库中，**磁盘上没有明文令牌**
6. 服务与进程全部清理
